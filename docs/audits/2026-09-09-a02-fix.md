# A02 — подтверждение email при принятии приглашения

Статус: **закрыто в репозитории**, 2026-09-09. База рабочего дерева:
`5bc91990e829fcce3d48935c66eb27ea324a7086`; исправление пока не закоммичено.

## Что исправлено

Прежде `ResolveTenant` передавал email профиля в автоматическую привязку
приглашения. Проверка владения адресом отсутствовала: действительный OIDC
пользователь с неподтверждённым чужим email мог получить роль приглашения.

Теперь `Principal.VerifiedEmail` формируется только из аутентифицированного
UserInfo, где одновременно присутствуют подходящий email и boolean
`email_verified: true`. Сохраняются проверки issuer, client, совпадения subject,
expiry и application session. Признак подтверждения относится только к email
из этого же ответа; его нельзя применить к fallback email из токена/профиля.
Token-only `email_verified=true` не является альтернативным доказательством.

Обычный email профиля остаётся отдельным полем. Репозиторий принимает явный
`MemberIdentity`, а authorization lookup передаёт только subject. Без
VerifiedEmail возможен вход уже привязанного активного участника, но нельзя
принять новое приглашение. Существующие транзакция и unique constraints
сохраняют атомарность привязки и повторный вход без изменения версии.

## Проверенные результаты

| Сценарий | Результат |
| --- | --- |
| UserInfo email совпадает, `email_verified=true` | Приглашение становится active, subject привязан, разрешена его DB-роль |
| `email_verified=false` | Новый пользователь получает 403; приглашение полностью неизменно |
| Признак отсутствует или null | То же: proof отсутствует, привязки нет |
| В токене `true`, в UserInfo `false`/нет признака | Token claim не даёт принять приглашение |
| UserInfo `true`, но email есть только в токене | Profile fallback не получает ownership proof, ответ 403 |
| UserInfo подтверждает другой адрес | Чужое admin-приглашение не принимается, ответ 403 |
| Неверный email или адрес с display name | Не создаётся invitation proof |
| Признак строкой/числом или subject UserInfo не совпадает | 401, invitation state не меняется |
| После отказа приходит действительное подтверждение | Приглашение можно принять; отказ его не расходует |
| Повтор успешного входа | Та же привязка, версия повышена только один раз |
| Уже привязанный viewer предъявляет email admin-приглашения | Чтение доступно, admin-операция получает 403; обе записи неизменны |
| У bound viewer `false`/нет признака | Его существующий вход сохраняется, роль не повышается |
| Отключённый участник | Доступ остаётся запрещённым, другое приглашение не активируется |
| Подтверждённый email, приглашение в другом workspace | 403; чужая запись неизменна под forced RLS |

A02 проверена через настоящий `NewProductionHandler`, OIDC authenticator,
tenant resolver, DB role authorizer, session/membership repositories и
PostgreSQL 18.6. Локальный TLS UserInfo fixture принимает ровно один
синтетический credential. Это не проверка живого Keycloak/OAuth flow или
криптографической проверки подписи IdP; такой результат здесь не заявляется.

## Контракты и применение

[ADR-0187](../../adr/0187-verified-email-invitation-binding.md) описывает
доверие к UserInfo и совместимость. OpenAPI документирует обязательное
подтверждение владения email; SDK regenerated source hashes обновлены,
публичные сигнатуры и схемы не меняются. Новое поле остаётся в памяти запроса
и исключено из JSON; новых persisted/event/public полей и retention paths нет.

Для применения необходимо обновить все API instances и настроить IdP так,
чтобы UserInfo возвращал реальный email и boolean-результат проверки владения.
Нельзя заменять отсутствующее доказательство постоянным `true` mapper.
Существующий development-only bootstrap первого admin не изменён.

Рабочий Docker stack не пересобирался и не перезапускался. Старые привязки не
отзываются автоматически: у них нет сохранённого исторического proof. При
подозрительных прежних принятиях приглашений нужен разбор membership и
governed disable/session revocation, а не автоматическое удаление всех ролей.
A09, A10 и остальные незавершённые пункты Task 234 остаются открытыми.
