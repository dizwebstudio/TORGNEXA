## Воспроизведённые проблемы

### A01. Данные предыдущего пользователя остаются в браузерном кеше

Исправлено 2026-09-09; ниже сохранено исходное воспроизведение.
[Исправление и проверки](2026-09-09-a01-fix.md).

Места: [App.tsx](../../frontend/src/app/App.tsx), строки 14–16; [AuthProvider.tsx](../../frontend/src/auth/AuthProvider.tsx), строки 84–89; [OrderList.tsx](../../frontend/src/features/orders/OrderList.tsx), строки 34–38.

`QueryClient` создаётся выше `AuthProvider` и сохраняется при logout/login. Выход очищает только сессию. Ключ списка заказов — `['orders','shell',q,status,cursor]` — не содержит идентификатора пользователя или workspace. Срок свежести — 20 секунд. Аналогичные общие ключи есть у финансовых данных и отчётов.

При смене пользователя в той же открытой SPA новый пользователь может получить старый результат из памяти ещё до обращения к API. Ошибка нового запроса также не обязательно скрывает старые данные: список проверяет `query.isError && !query.data`. Серверный RLS этот путь отображения не контролирует.

Проверка с установленным `QueryClient/QueryObserver` и теми же параметрами показала:

```text
newIdentitySees: {items: [{order_number: 'SYNTHETIC-WORKSPACE-A-ORDER'}]}
secondUserRequests: 0
```

Это проверка поведения кеша и анализ lifecycle приложения, не полный браузерный тест двух реальных OIDC-аккаунтов.

Исправление: создавать/сбрасывать кеш на границе identity + workspace, отменять незавершённые запросы старого пользователя, исключить их позднюю запись в новый кеш. Обработать также истечение сессии, смену аккаунта и изменение прав. Добавить browser regression A → logout → B, включая ошибку загрузки данных B.

### A02. Неподтверждённый email используется для активации приглашения

Исправлено 2026-09-09; ниже сохранено исходное воспроизведение.
[Исправление и проверки](2026-09-09-a02-fix.md).

Места: [oidc_security.go](../../internal/app/api/oidc_security.go), строки 215–226 и 364; [members.go](../../internal/platform/postgres/tenancyrepo/members.go), строки 94–99.

В `oidcClaims` и `userInfoClaims` нет поля `email_verified`. Значение email попадает в `Principal.Email`, после чего `ResolveActiveMember` активирует ещё не привязанное приглашение с совпадающим email и назначает ему текущий subject.

Условия риска: действительный OIDC-токен для соответствующего workspace; учётная запись ещё не привязана в этом workspace; провайдер позволяет задать чужой неподтверждённый email; существует приглашение на этот адрес. Тогда можно получить роль из чужого приглашения. Для уже активного участника поиск по subject выполняется первым — это не безусловное повышение прав любого viewer. Отключённая самостоятельная регистрация в bundled Keycloak ограничивает один из путей эксплуатации, но не заменяет проверку владения email на границе приложения.

Тест вернул успешную аутентификацию и `Principal.Email=invited-admin@example.test` при `email_verified:false`. Проверялась обработка ответа доверенного UserInfo; подделка JWT-подписи не моделировалась.

Исправление: отделить email для профиля от подтверждённого email для авторизации; разрешать автоматическую привязку только при подтверждении владения адресом доверенным issuer либо через отдельное подтверждение приглашения. Не считать отсутствие claim подтверждением. Значение `email_verified` определено в [OpenID Connect Core, Standard Claims](https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims).

### A03. Повтор payment webhook не восстанавливает неуспешное изменение платежа

Исправлено 2026-09-09; ниже сохранено исходное воспроизведение. [Исправление и проверки](2026-09-09-webhook-fixes.md).

Места: [payment_webhooks.go](../../internal/app/api/payment_webhooks.go), строки 123–141; [paymentsrepo/repository.go](../../internal/platform/postgres/paymentsrepo/repository.go), строки 343–364.

`RecordWebhookEvidence` выполняет собственную транзакцию. Затем API отдельно вызывает `applyVerifiedStatus`. Если изменение статуса конфликтует по версии, падает или процесс останавливается между операциями, receipt уже существует. Повтор получает `fresh=false` и прекращает обработку.

В тесте первый `ChangePaymentStatus` возвращал optimistic conflict; второй вызов был бы успешным. После двух доставок получено:

```text
delivery 1 HTTP 200
delivery 2 HTTP 200
status=created, status calls=1, receipts=1
```

Исправление: после проверки провайдером передавать результат в одну repository-операцию, которая атомарно записывает receipt, payment transition, audit и outbox; либо хранить pending receipt с гарантированным worker retry. Reconciliation остаётся полезной страховкой, но текущий webhook сам уже не восстановится. Проблема ранее зафиксирована в 234.2 и всё ещё воспроизводится.

### A04. Внутренний сбой webhook подтверждается как успешная доставка

Исправлено 2026-09-09 после независимой проверки подлинности; ниже исходное воспроизведение. [Исправление и границы](2026-09-09-webhook-fixes.md).

Место: [payment_webhooks.go](../../internal/app/api/payment_webhooks.go), строки 124–128. Аналогичный подход: [commerce_webhooks.go](../../internal/app/api/commerce_webhooks.go), строки 130–133, и [social_webhooks.go](../../internal/app/api/social_webhooks.go).

При ошибке записи уже проверенного payment webhook обработчик отвечает HTTP 200 без receipt и без durable retry. Провайдер получает подтверждение и может прекратить повторные доставки. Для commerce/social ошибка publication также заканчивается успешным ответом.

Failure injection в payment repository подтвердил `HTTP 200; receipts=0` при временной ошибке БД. Другие семейства сверены по коду, отдельно не воспроизводились.

Исправление: сохранять одинаковые ответы до проверки подлинности, а после неё подтверждать доставку только после durable commit. Временный внутренний сбой должен давать retryable ответ либо гарантированную внутреннюю очередь. Это отдельный дефект от A03: одного объединения SQL-транзакций недостаточно, если rollback всё равно получает 200.

### A09. Первый параллельный запрос одной сессии вызывает гонку INSERT

Исправлено 2026-09-10; ниже сохранено исходное воспроизведение.
[Исправление и проверки](2026-09-10-a09-fix.md).

Места: [securitysettingsrepo/repository.go](../../internal/platform/postgres/securitysettingsrepo/repository.go), строки 32–39; преобразование ошибки в отказ аутентификации — [oidc_security.go](../../internal/app/api/oidc_security.go), строки 215–216.

`SELECT ... FOR UPDATE` не блокирует отсутствующую строку. Несколько запросов новой сессии одновременно видят отсутствие строки и выполняют обычный INSERT. Один коммитится, остальные получают нарушение уникальности. Любая ошибка `Observe` превращается в `ErrUnauthenticated` и HTTP 401.

Проверка использовала реальный repository, PostgreSQL 18.6, DDL существующей миграции и непривилегированную роль с forced RLS. Тестовый BEFORE INSERT trigger добавлял задержку 0,5 секунды, чтобы воспроизводимо раскрыть естественное окно гонки. **7 из 8** запросов завершились `SQLSTATE 23505`; это результат искусственно синхронизированного теста, не измеренная частота production-сбоев.

Исправление: идемпотентный insert с обработкой конфликта и повторной проверкой существующей строки; сохранить запрет возвращения revoked-сессии в active и единственность login event. Ошибки инфраструктуры следует отличать от недействительных credentials. Одноразовая база после проверки удалена.

### A10. Realtime-поток не переживает общий таймаут записи

Исправлено 2026-09-10; ниже сохранено исходное воспроизведение.
[Исправление и проверки](2026-09-10-a10-fix.md).

Места: [realtime.go](../../internal/app/api/realtime.go), строки 75–97; [config.go](../../internal/platform/config/config.go), строка 201; [api.go](../../internal/app/api/api.go), строка 504.

Общий `http.Server.WriteTimeout` равен 10 секундам по умолчанию. SSE не обновляет write deadline, а heartbeat отправляется каждые 15 секунд. После истечения deadline следующая запись/flush не доходит до клиента, вызывая переподключение и дополнительные auth/DB-запросы.

В тесте настоящий HTTP-сервер использовал тот же механизм deadline, сокращённый до 100 мс. Через 2 секунды backend обнаружил новый audit ID; клиент получил только `ready`, без `invalidate`.

Исправление: управлять write deadline для SSE отдельно, ограничивать время каждой записи и проверять ошибки flush; добавить heartbeat/cancel/slow-client тесты на реальном сервере. Дополнительно нужна стратегия восстановления пропущенных изменений при reconnect: сейчас `ready` не инвалидирует кеш, а новый stream начинает с текущего audit head.

## Дополнительные проблемы, подтверждённые анализом кода

### A05. Timeout создания платежа записывается как окончательный отказ

Места: [payments.go](../../internal/app/api/payments.go), строки 301–308; [payments.go, state machine](../../internal/core/payments/payments.go), строки 94–116; [payment_reconciliation.go](../../internal/app/worker/payment_reconciliation.go), строки 173–189.

Любая ошибка `gateway.CreatePayment`, включая потерю ответа после успешного remote create, отправлялась в ветку перехода `failed` без remote ID. Уточнение интеграционной проверки: валидатор репозитория запрещал такую запись, поэтому `failed` не сохранялся; локальное намерение оставалось `pending`, а API возвращал ошибку. Повтор запроса снова вызывал remote create. Reconciliation ищет локальные платежи по remote ID и не найдёт такую запись; переход `failed → succeeded` также запрещён. Комментарий о сохранении `pending` после сбоя противоречит реализации.

Исправление: отличать доказанный отказ от неопределённого результата; сохранять незавершённое намерение и восстанавливать связь по исходному external/idempotency key через разрешённые provider capabilities. Не повторять списание с новым ключом. Это согласуется с ADR-0079. Изменение state machine потребует согласованных контрактов, схемы хранения и тестов timeout-after-acceptance.

### A06. Изменение роли и audit не имеют общей транзакции

Места: [member_settings.go](../../internal/app/api/member_settings.go), строки 140–152; [members.go](../../internal/platform/postgres/tenancyrepo/members.go), `UpdateMember`; аналогичный порядок есть в `identity_provider_settings.go` и `user_profile.go`.

`UpdateMember` возвращает уже закоммиченное изменение. Последующий `audit.Capture` может завершиться ошибкой: API отдаст 500, но новые права останутся в БД без обязательной audit-записи. Падение процесса между вызовами даёт тот же разрыв. Для некоторых других settings-путей replay пропускает Capture, поэтому повтор запроса также не является надёжным восстановлением.

Исправление: authoritative audit или durable audit intent в транзакции privileged mutation. Это открытый blocker 234.3. Исправление гонки последнего администратора из 234.1 уже присутствует: repository использует workspace advisory lock; считать её всё ещё неустранённой оснований по текущему коду нет.

### A07. Проверка topic commerce webhook сравнивает заголовок с ним же

Места: [commerce_webhooks.go](../../internal/app/api/commerce_webhooks.go), строки 118–123; [commerce_webhook.go](../../internal/platform/connectors/commerce_webhook.go), строка 28; [WooCommerce webhook](../../connectors/storefronts/woocommerce/webhook.go), строки 43–78.

API заполняет `HeaderTopic` и `ExpectedTopic` одним значением из запроса. SDK-проверка их равенства становится бессмысленной. В WooCommerce подпись здесь проверяется по body, а тип события и resource kind берутся из ExpectedTopic. Обладая ранее подписанным body/signature, отправитель может изменить неподписанный topic. Для ещё не принятой доставки подменённая классификация также может занять dedup ID и поглотить правильный вариант.

Исправление: получать ожидаемый topic из доверенной серверной subscription configuration/reference и сопоставлять его с запросом. Подпись body не заменяет эту привязку. Проблема уже описана в 234.4; отдельный live exploit не выполнялся.

### A08. OAuth refresh удерживает соединение, пока ждёт второе из того же пула

Места: [secretrepo/repository.go](../../internal/platform/postgres/secretrepo/repository.go), строки 81–90 и 366–383; [token_manager.go](../../internal/platform/connectorauth/token_manager.go), строки 117–142.

`WithRefreshLock` удерживает транзакцию и вызывает callback. Callback читает bundle через SecretProvider и вращает секрет, открывая дополнительные транзакции того же пула. При `MaxOpenConns=1` операция ждёт сама себя до отмены контекста; при большем пуле аналогичное исчерпание возможно при параллельном refresh разных аккаунтов. `pg_try_advisory_xact_lock` снимает ожидание занятого ключа, но не решает случай разных успешно захваченных ключей.

Исправление: единая SQL connection/transaction boundary для координации и работы с секретом либо отдельный ограниченный coordinator pool с гарантированным резервом. Увеличение пула само по себе не устраняет причину. Сценарий повторно проверен по коду, отдельный DB-тест refresh в этом аудите не запускался; задача 234.5 остаётся актуальной.

## Оптимизация

1. **Сократить стоимость каждого авторизованного запроса.** Сейчас выполняются внешний UserInfo HTTP-вызов, транзакция Observe с обновлением сессии и два ResolveActiveMember — в tenant resolver и authorizer. Это минимум три служебные DB-транзакции до бизнес-запроса. Передавать один database-authoritative member через typed context, объединять обновления last_seen, затем внедрять локальную JWT-проверку с корректным JWKS cache/rotation и сохранением fail-closed revocation. Основание: 234.6 и текущий OIDC-код.

2. **Один watcher на workspace вместо одного polling-цикла на вкладку.** `LatestID` открывает транзакцию, применяет scope и читает audit head каждые 2 секунды для каждого SSE-клиента. Для 1000 подключений это расчётно около 500 транзакций в секунду даже без изменений данных. Это оценка по алгоритму, не нагрузочное измерение. Нужны общий tenant broadcaster, ограниченные буферы и лимиты подключений.

3. **Убрать общий mutex и полный sweep из limiter hot path при росте нагрузки.** Текущий лимитер ограничивает cardinality, что хорошо, но все запросы сериализуются на одном mutex, а раз в минуту под ним просматривается вся карта. Для single-node — sharding/очередь истечения; для нескольких реплик — общий бюджет через Valkey с явно заданным поведением при сбое. Это 234.8, а не требование менять архитектуру modular monolith.

4. **Закрепить стоимость в измерениях.** Нагрузочный профиль должен включать настоящий auth/membership/session path, несколько вкладок одного tenant, SSE reconnect, одновременный refresh и деградацию IdP/БД. Метрики: IdP calls/request, DB transactions/request, pool wait, session lock wait, SSE clients/watchers и p95/p99. До измерений не обещать конкретный процент ускорения.
