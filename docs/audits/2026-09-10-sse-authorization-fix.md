# SSE — повторная проверка доступа открытого соединения

Статус: **закрыто в репозитории**, 2026-09-10. База рабочего дерева:
`9524d8c5220a075626d31d04c83ff5a900070a73`; это продолжение A10 и Task 234.7.

## Исправление

Ранее SSE сохранял решение о доступе на всё время соединения. Regression-тест
подтвердил: после отзыва разрешения поток оставался открытым до принудительной
отмены клиента через 17 секунд.

Теперь каждый открытый поток каждые 15 секунд повторяет существующую цепочку
OIDC/session → canonical tenant/membership → permission. На всю проверку
выделено 5 секунд. Отказ, недоступность зависимости или timeout отменяют поток.
Monitor выполняет проверки последовательно, отменяется и завершается вместе
с обработчиком. Успех, вернувшийся после deadline, не восстанавливает доступ.

Соединение связано с исходными issuer, subject, session/subject references,
organization/workspace, expiry и permission. Роли и каноническое членство
проверяются заново. Подменить identity/tenant/session или продлить expiry
внутри потока нельзя; новый токен требует нового авторизованного соединения.

Первоначальный expiry токена отдельно ограничивает context и deadline каждой
записи. Поэтому он завершает поток без ожидания очередной проверки, включая
блокирующую запись медленному клиенту. До открытия SSE отсутствие доверенной
привязки или допустимого expiry означает отказ. После начала передачи отказ
закрывает поток без JSON, auth events или внутренних ошибок в SSE payload.

## Проверенные сценарии

| Сценарий | Результат |
| --- | --- |
| Полномочия сохранены, новая допустимая роль | Повторная проверка успешна; authorizer получает свежий context и исходный permission |
| Изменены identity/session/tenant/expiry или удалено разрешение | Доступ отклоняется; реальный HTTP-поток закрывается при потере permission |
| Истёк токен, следующая проверка назначена через час | Реальные TLS HTTP/1.1 и HTTP/2 завершаются по expiry без второго Authenticate |
| Клиент прекратил читать | http.Server/net.Pipe освобождает обработчик по expiry 500 мс, раньше обычного бюджета кадра 5 с |
| Ошибка IdP, timeout, поздний успех, cancel во время проверки | Поток закрывается; monitor не остаётся после обработчика и не повторяет отказавшую проверку |
| Реальная PostgreSQL: активная сессия | Поток переживает несколько проверок, сохраняются одна сессия и одно session_observed |
| Реальная PostgreSQL: Revoke или disabled member | Поток закрывается; revoked/disabled state не восстанавливается; отзыв имеет единственное событие |
| Реальная PostgreSQL: SELECT membership / UPDATE session запрещены | Повторная проверка завершается отказом и закрывает поток |
| Production OIDC: UserInfo возвращает другой subject | Поток закрывается |
| Прежние A10 HTTP и Chrome regressions | Deadlines, reconnect refresh, metadata-only frames, coalescing и logout сохранены |

## Применение, стоимость и границы

Для применения обновить все API instances и завершить старые соединения.
Развёртывание не выполнялось. Миграций, новых зависимостей, persisted/public
полей и изменения frontend runtime нет. ExpiresAt — приватное поле Principal,
исключённое из JSON; guard не копирует bearer token, request, profile или email
в свой context value. OpenAPI описывает поведение, SDK обновлён по source hash
без изменения операций/сигнатур. Retention сессий и audit не меняется.

Отзыв периодический: до следующей проверки проходит до 15 секунд, сама
проверка имеет бюджет 5 секунд. Уже начатая запись сохраняет свой ограниченный
deadline; переданные/буферизованные байты отозвать нельзя. Это не обещание
мгновенного logout или жёсткого срока закрытия TCP через внешний proxy.
Expiry независимо ограничивает context и записи.

Цена — до четырёх дополнительных полных auth-проверок в минуту на соединение
с UserInfo, session observation и двумя текущими membership lookups. JWKS,
устранение повторных lookup, throttle last_seen, shared watcher, ограничения
клиентов и нагрузочные профили остаются в 234.6/234.7.

Интеграционные тесты используют настоящие PostgreSQL/HTTP и production
composition, но синтетический локальный TLS UserInfo. Chrome отдельно
проверяет настоящий frontend с синтетическим transport. Живой production
IdP/proxy, нагрузочная квалификация и capacity этим результатом не заявляются.
