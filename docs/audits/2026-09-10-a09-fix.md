# A09 — конкурентная регистрация OIDC-сессии

Статус: **закрыто в репозитории**, 2026-09-10. База рабочего дерева:
`5bc91990e829fcce3d48935c66eb27ea324a7086`; исправление пока не закоммичено.

## Что исправлено

При первых параллельных запросах одной сессии `SELECT ... FOR UPDATE` не
блокировал отсутствующую строку. Несколько транзакций выполняли обычный INSERT,
проигравшие получали unique violation, а OIDC authenticator превращал его в 401.
Новый интеграционный тест до исправления воспроизвёл семь ложных 401 из восьми
HTTP-запросов через реальную auth/tenant/authz цепочку.

Теперь первая регистрация использует `ON CONFLICT ... DO NOTHING`. Только
создатель строки пишет `session_observed` в той же транзакции. Конкурент,
проигравший INSERT, отдельным READ COMMITTED запросом читает строку под
`FOR UPDATE`, проверяет статус и subject и обновляет активную сессию.
Отозванная сессия не активируется повторно, subject не перепривязывается.
Обычный путь существующей сессии сохраняет прежнее число SQL-запросов;
производственный пул не увеличивался, блокировка в памяти процесса не добавлялась.

Неверная или отозванная сессия по-прежнему даёт 401. Ошибки хранилища сессий
дают 503 с `Retry-After: 5`, `Cache-Control: no-store`, без `WWW-Authenticate`
и внутренних подробностей. Ошибки отмены/таймаута сохраняют эту классификацию,
включая отмену до начала Observe. Доступ запрещён, бизнес-обработчик не запускается.
Это изменение относится к session store; обработка сбоев UserInfo и membership
остаётся за пределами A09.

## Проверенные результаты

| Сценарий | Результат |
| --- | --- |
| 8 первых запросов, 2 независимых application pools по 4 соединения | Все HTTP 204; одна сессия и один `session_observed` |
| Две следующие серии по 8 запросов | Все HTTP 204, повторных login events нет |
| 8 запросов после Revoke | Все HTTP 401; revoked-строка неизменна, по одному событию отзыва и audit record |
| Revoke держит строку первым | Observe ждёт commit, затем отклоняет сессию без изменения timestamps |
| Observe держит строку первым | Наблюдение завершается до Revoke; следующие Observe отклоняются |
| Отмена до Observe и во время заблокированного первого INSERT | Ошибка отмены не маскируется как invalid; нет сессии/события, повтор успешен |
| Ошибка INSERT login event через настоящий API | HTTP 503, сессия и событие откатываются; после восстановления три запроса успешны и дают одну пару записей |
| Новое, затем запоздалое наблюдение | last_seen/expires не уменьшаются; first_seen/authenticated_at/client_kind/subject не переписываются |
| Та же ссылка с другим subject | Отказ, исходная сессия неизменна |
| Та же ссылка в другом workspace | Независимая сессия; чужие данные не смешиваются |
| Ошибка хранилища через security composition | 503 без DB-подробностей и credential challenge; защищённый обработчик не запускается |

Конкуренция воспроизводится тестовым PostgreSQL trigger/barrier: все восемь
запросов достигают INSERT до освобождения блокировки. Порядок Observe/Revoke
подтверждается настоящим ожиданием row lock. Эти барьеры существуют только
в одноразовой тестовой БД и не добавлены в production-код.

## Контракты, применение и границы

[ADR-0188](../../adr/0188-concurrent-oidc-session-observation.md) фиксирует
алгоритм и совместимость. OpenAPI описывает общий ответ 503 при сбое session
store; SDK regenerated source hashes обновлены. Сигнатуры API/SDK, event
schemas, SQL-схема, persisted fields и retention не меняются. Клиент должен
обрабатывать такой 503 как временную недоступность; повтор мутации сохраняет
обычные требования идемпотентности соответствующего endpoint.

Для применения обновить все API instances: старые экземпляры при смешанном
развёртывании ещё могут выдавать ложный 401. Миграция и переписывание истории
сессий не требуются. Рабочий Docker stack не пересобирался и не перезапускался.

Проверки использовали PostgreSQL 18.6, forced RLS и непривилегированную
application role. UserInfo был локальным TLS fixture с синтетическими
credentials. Живой Keycloak/OAuth flow, JWT signature/JWKS и производительная
нагрузка production не проверялись. Уже авторизованный до Revoke запрос может
завершиться; глобальная отмена таких запросов и provider-wide logout не входят
в это исправление. Браузерные сценарии A01 повторно не запускались.

Из исходного аудита A01–A10 остаётся A10. Более широкая Task 234 сохраняет
открытые работы, в том числе JWKS, уменьшение membership/IdP calls, throttle
last_seen и метрики authenticated hot path из 234.6.
