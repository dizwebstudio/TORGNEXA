# A10 — таймауты SSE и восстановление после переподключения

Статус: **закрыто в репозитории**, 2026-09-10. База рабочего дерева:
`5bc91990e829fcce3d48935c66eb27ea324a7086`; изменения пока не закоммичены.

## Что исправлено

SSE наследовал общий `http.Server.WriteTimeout` (10 секунд по умолчанию),
хотя первый heartbeat приходил через 15 секунд. Ошибки Flush не проверялись.
Кроме того, новый поток начинал с текущего audit head, а ready не обновлял кеш:
изменение за время разрыва могло остаться незаметным для браузера.

Теперь после прохождения auth/tenant/authz SSE снимает общий write deadline.
Отправка и Flush каждого кадра получают отдельный срок в пять секунд; после
успеха deadline снимается на время ожидания. Ошибка управления deadline,
записи или Flush завершает обработчик. Обычные HTTP timeouts не менялись.
Если ResponseWriter не поддерживает необходимые механизмы, поток не запускается.

После ready сервер всегда отправляет invalidate с reason connected. Браузер
перечитывает разрешённые API, включая изменения за время разрыва соединения.
Это работает и при прежнем/пустом cursor. Cursor остаётся метаданными начального
состояния, а не указателем durable replay; Last-Event-ID не восстанавливает
историю. Heartbeat не инициирует повторные запросы, существующее объединение
сигналов за 150 мс сохранено. Frontend runtime менять не потребовалось.

## Проверенные результаты

| Сценарий | Результат |
| --- | --- |
| До исправления, настоящий TLS HTTP/1.1 и HTTP/2 | Поток обрывается после установленного WriteTimeout; ожидаемый провал regression-теста |
| Два heartbeat-интервала длиннее обычного timeout и бюджета отдельного кадра | Соединение живо, оба heartbeat доставлены |
| Audit head меняется после этих интервалов | Клиент получает invalidate с новым cursor |
| Клиент отменяет запрос | Обработчик завершается, поток освобождается |
| Reconnect с изменённым, прежним и пустым head | ready и явный invalidate/connected; разрыв не считается подтверждением актуальности кеша |
| Медленный клиент перестаёт читать | Настоящий http.Server/net.Pipe блокируется на следующем Flush и освобождает обработчик по deadline без client close/cancel |
| Обычный API-ответ задержан за WriteTimeout | HTTP/1.1 и HTTP/2 сохраняют ограничение и завершаются ошибкой |
| Нет аутентификации или разрешения | 401/403; SSE и чтение audit head не запускаются |
| Ошибка frame deadline, Write, FlushError, снятия deadline | Обработчик завершается без продолжения polling и раскрытия внутренних ошибок |
| Нет deadline support / первоначальная ошибка control | До начала SSE возвращается 501 / 503 |
| Настоящий браузер: заказ изменён во время разрыва | После reconnect новая версия заказа отображается через один повторный API-запрос, даже при прежнем cursor |
| Разделённый на chunks SSE-кадр и восемь invalidate подряд | Parser собирает кадр; серия даёт один refetch |
| ready/heartbeat и logout | Liveness не вызывает refetch; logout отменяет поток, дальнейших reconnect/refetch нет |

Payload проверяется как metadata-only `{reason,cursor,at}` с UTC timestamp.
Контракт OpenAPI и generated SDK hashes обновлены; публичные сигнатуры,
SQL-схема, event-bus schemas и persisted fields не менялись.

## Применение и границы

Для применения обновить все API instances: старые экземпляры могут по-прежнему
обрывать SSE и не отправлять connected invalidation. Новая миграция и изменение
frontend runtime не нужны; одна дополнительная загрузка при подключении
предусмотрена для восстановления актуальности данных. Рабочий Docker stack
не пересобирался и не перезапускался, развёртывание не выполнялось.

Серверные проверки используют настоящий HTTP/TLS и production route composition
с синтетическими auth/audit dependencies. Браузерная проверка использует настоящие
React/Query/SDK и hook, но подменяет auth/API/SSE transport. Эти проверки
выполнены отдельно; это не сквозной прогон живого IdP/PostgreSQL/proxy stack.
Миграции и DB-операции A10 не менялись, PostgreSQL gate повторно не запускался.

Масштабирование SSE, ограничения числа клиентов, общий tenant watcher и
нагрузочная квалификация остаются в 234.7. На момент A10 полномочия проверялись
при открытии соединения. Последующее
[исправление повторной авторизации](2026-09-10-sse-authorization-fix.md)
закрывает follow-up по expiry/revoke/изменению прав; его новые проверки и
журналы приведены отдельно. SSE не гарантирует replay каждого события
и не заменяет проверку ошибок/повторов обычных API при refetch.

Исходный список A01–A10 закрыт в репозитории. Более широкая Task 234 остаётся
`in_progress` с явно отмеченными незавершёнными подзадачами.
