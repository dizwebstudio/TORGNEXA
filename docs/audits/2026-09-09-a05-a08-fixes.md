[ADR-0184](../../adr/0184-audit-transaction-and-webhook-topic-binding.md).

| Пункт | Исправление | Проверка |
| --- | --- | --- |
| A05 | Неопределённый create остаётся `pending`; retry не повторяет запрос провайдеру. Worker связывает платёж по `external_id` с проверкой account/amount/currency, затем применяет статус. Исправлен UUIDv5 audit ID, блокировавший реальную запись worker. | Реальная PostgreSQL + HTTP-сервер, принявший POST и оборвавший ответ; повторные запросы; reconciliation success/cancel, неверная сумма/account, отсутствие external ID и отсутствие дублей audit/outbox. |
| A06 | Изменение настроек и аудит коммитятся вместе. Репозитории используют одну транзакцию; идемпотентный replay не повторяет Capture. | Ошибка реального INSERT audit через PostgreSQL trigger: откат role/status, профиля, draft/activate/disable IdP; успешный retry и ровно одна запись аудита на изменение. |
| A07 | Случайный reference связан с точным topic в серверной конфигурации. Подмена topic отклоняется до Inbox, подпись остаётся обязательной. | HTTP handler → реальный WooCommerce verifier → encrypted SecretProvider → PostgreSQL Inbox/Outbox: подмена topic/reference/signature, отсутствие/дублирование reference, верная доставка после атаки, replay и отзыв подписки. Saleor: несовпадение подписанного body event с topic. |
| A08 | Advisory lock, чтение и encrypted rotation используют одно соединение. | Реальная PostgreSQL, `MaxOpenConns=1` и 4, параллельные аккаунты/повторы, одна ротация, отказ refresh, cancel, rollback и повторный захват lock. |

Уточнение первоначального A05: старый код **пытался** перевести платёж в
`failed` без remote ID, но валидатор репозитория отклоняет такую запись. Поэтому
утверждение об уже сохранённом terminal `failed` было слишком сильным. Реальные
дефекты — ошибочный API-результат, повтор remote create на retry и отсутствие
восстановления по исходному external ID — закреплены тестами и исправлены.

## Подключение webhook после обновления

Параметр `subscription` теперь обязателен. Выделите окно обслуживания и
приостановите callback у провайдера до изменения конфигурации и URL.

1. Сгенерируйте отдельный reference для каждого topic:
   `python3 scripts/new-commerce-webhook-reference.py product.updated`.
   Команда выводит приватный `callback_query` и безопасный `configuration_binding`.
2. После обновления API/worker добавьте `configuration_binding` в массив
   `commerce_webhook_subscriptions` существующей runtime configuration аккаунта
   через `PUT /api/v1/connector-accounts:runtime-config` с актуальным
   `expected_version` и `Idempotency-Key`. Сохраните остальные поля конфигурации.
3. Добавьте выданный `?subscription=...` к callback URL конкретной подписки
   WooCommerce/Saleor. Один reference соответствует одному exact topic.
4. Возобновите callback и выполните синхронизацию интервала обслуживания.

В JSON-конфигурацию записываются только `reference_sha256` и `topic`, не сам
reference. Для отзыва удалите binding; для ротации замените digest и callback URL.
Не записывайте query string callback в журналы reverse proxy. Подписанный body и
подпись по-прежнему проверяются. Старые URL без reference получают одинаковый
ответ `200`, но события не публикуются.

## Воспроизведение проверок

```bash
./scripts/check-audit-postgres.sh
```

Нужны Docker, Go из `go.mod`, Python 3, jq и локальный PostgreSQL image из
release inventory. При необходимости задайте `TORGNEXA_TEST_POSTGRES_IMAGE`.
Скрипт создаёт контейнер без сети/публикации портов, применяет все миграции,
запускает `go test -race` для A05–A08 и удаляет контейнер. Тесты используют
синтетические данные и не обращаются к реальным платёжным/IdP сервисам.
Обычный `go test ./...` пропускает PostgreSQL-сценарии без двух явно заданных
`TORGNEXA_TEST_*DATABASE_URL`; скрипт задаёт их автоматически.

## Границы результата

Остальные пункты аудита A01–A04, A09–A10 не входили в этот набор исправлений.
A03–A04 исправлены следующим этапом: [webhook](2026-09-09-webhook-fixes.md).
Более широкая задача 234.3 (все security/connector-account mutations), метрики
OAuth и полный исторический recovery остаются в backlog. При отсутствии
подтверждающего provider observation платёж сохраняет `pending`; повторное
списание автоматически не запускается.

Обнаружено отдельное расхождение: каталог storefront и текущие Go-манифесты
WooCommerce/Saleor используют разные family. Интеграционный тест проверяет
действующий `marketplace` binding реального адаптера. Унификация family требует
отдельной миграции/совместимости существующих аккаунтов и не включена сюда.
