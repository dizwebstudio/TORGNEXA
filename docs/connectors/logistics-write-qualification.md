# Квалификация записывающих операций доставки

Этот документ фиксирует текущую границу runtime для перевозчиков. Наличие
операции в SDK или `manifest.json` не означает, что она доступна в production:
remote write включается только после проверки схемы запроса, локальной
идемпотентности, approval/audit, read-after-write или reconciliation и
непродакшеновых fixtures.

## Текущее состояние

| Перевозчик | Доступно в runtime | Пока закрыто |
|---|---|---|
| СДЭК | проверка кабинета, ПВЗ, расчёт тарифа, чтение статуса, создание и отмена отправления, отказ с возвратом в интернет-магазин, клиентский возврат с отдельным тарифом, этикетка, проверка `ORDER_STATUS` вебхука | — |
| ПЭК | проверка кабинета, терминалы/ПВЗ, расчёт тарифа, чтение статуса, bounded подача одной заявки самовывозом, отмена предварительного оформления, одиночная PDF-этикетка, печатная форма заявки, пакетная PDF-печать одной заявки, возврат одного принятого груза | отмена сформированного груза |
| Деловые Линии | проверка кабинета, терминалы/ПВЗ, расчёт тарифа, чтение статуса, создание отправления, заявка на отмену address-delivery, PDF-форма накладной | подтверждение/отклонение отмены, terminal/pickup-отмена и возврат |
| Почта России | проверка кабинета, отделения, расчёт тарифа, чтение статуса, PDF-этикетка, чтение партий в архиве, создание одиночного заказа в backlog, удаление нового заказа, формирование партии, передача сформированной партии в работу, перемещение партии в архив, возврат партии из архива, отдельное возвратное отправление (создание/редактирование/удаление) | прочие операции партий/документов |
| 5Post | проверка кабинета, ПВЗ, статус, отмена, этикетка | создание |
| Ozon Доставка | проверка кабинета | тариф, создание, отмена, статус, этикетка, ПВЗ |

Все доступные чтения ограничены по размеру запроса и ответа и возвращают
нейтральные поля. Provider-specific IDs и сырые ответы не становятся частью
Core.

## Следующий безопасный шаг

Для следующих записывающих операций нужен общий host-side контур:

1. связать команду с tenant-scoped `logistics_shipments`;
2. зарезервировать `Idempotency-Key` и digest до внешнего вызова;
3. выполнить capability, account-status, policy/approval и version checks;
4. сохранить только нормализованный результат, remote ID и bounded reason code;
5. при timeout оставить состояние `unknown` и передать его reconciliation, не
   повторяя внешний вызов вслепую;
6. записать audit и Transactional Outbox в одной локальной транзакции.

Создание и отмена СДЭК прошли локальную qualification boundary: для них не требуется
расширять товарную модель, но удалённый вызов разрешается только после
approval, capability, идемпотентной claim-записи и проверки версии. Номер
отправления предварительно разрешается в UUID; при создании неоднозначный результат
переводит отправление в `unknown` и не повторяется автоматически. Остаются
необходимыми sandbox/conformance fixtures и проверка точного ограничения
отмены и создания со стороны перевозчика перед production claim.

Оформление Деловых Линий прошло repository qualification boundary для
address-to-address LTL request: host передаёт только явные tenant-параметры
`requester_uid`, `sender_counteragent_id`, `freight_uid`, дату и окно передачи;
секрет используется для короткой login-сессии и не сохраняется. Ответ
принимается только при `metadata.status=200`, `data.state=success` и числовом
`requestID`; при сетевой неопределённости worker оставляет локальную операцию
`unknown` и не повторяет внешний вызов.

Отмена адресной доставки подключена отдельно: runtime вызывает официальный
`POST /v3/orders/cancel_delivery.json` с `appkey`, временным `sessionID`,
числовым `orderID` и `requester=sender`. Ответ `data.status=success` означает
только принятие заявки; worker сохраняет `cancellation_pending`, а не
подменяет его окончательным `cancelled`. Последующее чтение истории статусов
должно подтвердить или отклонить отмену; terminal/pickup-отмена и возврат
остаются закрытыми.

Проверка вебхука СДЭК принимает только событие `ORDER_STATUS` с UUID-доставкой
и повторно читает заказ через OAuth API. В callback не доверяются заявленные
статус и время; в PostgreSQL сохраняются только нормализованный статус,
идентификатор доставки и digest тела в append-only receipt. Полный клиентский
возврат СДЭК с отдельным тарифом остаётся закрытым.

Возврат СДЭК поддерживает два официальных варианта: `mail_type=refusal` вызывает
`POST /v2/orders/{uuid}/refusal` без тела, а `mail_type=client_return` вызывает
`POST /v2/orders/{uuid}/clientReturn` с обязательным `tariff_code`. В обоих
случаях номер отправления разрешается в UUID, а UUID ответа проверяется.

Почта России допускает создание одного заказа через официальный backlog:
runtime строго проверяет индексы РФ, адрес с номером дома, ФИО и одинаковые
габариты посылок, после чего принимает ровно один `result-id`. Формирование
партии выполняется через `POST /1.0/user/shipment`, передача сформированной
партии — через `POST /1.0/batch/{batch-name}/checkin`, перемещение партии в архив —
через `PUT /1.0/archive`, а возврат из архива — через `POST /1.0/archive/revert`;
все четыре операции защищены
approval, capability и tenant-scoped operation receipt. Check-in принимает
только явное подтверждение `f103-sent` и не повторяется автоматически после
неоднозначного результата. Удаление одного нового заказа уже доступно через официальный
`DELETE /1.0/backlog`: runtime отправляет один числовой ID и принимает только
точно совпавший `result-id`. Архивирование принимает только один числовой
номер партии и точное подтверждение имени партии. Возврат принимает один
числовой номер партии через `POST /1.0/archive/revert` и требует точного
подтверждения `batch-name`; результат нормализуется в `RESTORED` с
`archived=false`.
Standalone-возврат выполняется через `PUT /1.0/returns/return-without-direct`.
Host отправляет одну запись с российскими адресами, видом отправления,
объявленной ценностью и именами, а принимает только `position=0` с валидным
`return-barcode`. Публичный маршрут требует capability
`logistics.return.separate.create`, approval и tenant-scoped operation receipt;
адреса и имена не сохраняются в результате.

Удаление отдельной возвратной отправки выполняется через approval-bound
`DELETE /api/v1/logistics/returns/separate/{return_id}` и официальный
`DELETE /1.0/returns/delete-separate-return?barcode={barcode}`. Адаптер передаёт
только ШПИ и принимает `2xx` с пустым ответом либо пустым кодом; любой код
ошибки провайдера отклоняется. Результат нормализуется в `DELETED` и
`deleted=true`, а повтор защищён tenant-scoped operation receipt. Live
qualification должна подтвердить удаление только тестового возврата и
поведение при `RETURN_SHIPMENT_NOT_FOUND`/неоднозначном timeout.

Редактирование отдельной возвратной отправки выполняется через
approval-bound `POST /api/v1/logistics/returns/separate/{return_id}` и
официальный `POST /1.0/returns/{barcode}`. Адаптер отправляет полный bounded
набор адресов, вида отправления, ценности и имён, принимает только ответ с
тем же ШПИ и нормализует его в `UPDATED`/`updated=true`. Ошибочный или пустой
ответ провайдера не считается подтверждением; live qualification должна
использовать только disposable-тестовый возврат.

Официальный API ПЭК подтверждает отдельные bounded read-операции статуса и
лимит до 50 кодов в запросе; для предварительного оформления используется
`/preregistration/submit/` с обязательными sender/receiver/cargo полями, для
аннулирования предварительного оформления — `/order/cancellation/`, а для
PDF-этикетки, печатной формы заявки и пакетной печати — `/order/print/` с
типами `simple`, `big` и `multiple` соответственно: [документация ПЭК](https://test-kabinet.pecom.ru/preweb/api/v1/help/order).

В runtime включён только узкий create-маршрут: один заказ типа `orderType=0`
с отправителем из настроенного склада, российским получателем и сервисом
`pek_type_3`; он не создаёт сформированную перевозку автоматически. Отмена
сформированного груза и другие неподтверждённые записи остаются закрытыми.
Возврат принятого груза использует отдельный квалифицированный маршрут
`/cargos/cancelandreturncargo/`.
