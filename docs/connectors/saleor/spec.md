# Saleor Connector Spec

Family: `storefront`. Self-hosted (host-injected, admin-supplied like WooCommerce/Medusa/Shopware/Magento), a GraphQL-only API (there is no REST surface at all) against a per-merchant store host, authenticated with a single long-lived App access token.

Production networking is host-injected through a typed transport; provider code has no direct Core or SQL authority. Every request is a `POST /graphql/` carrying `{"query": ..., "variables": ...}`, authenticated with a Saleor "App" access token (Apps & webhooks > \<app\> > token) sent as `Authorization: Bearer <token>` -- unlike Shopware's client_credentials exchange, this token is minted once at app install/creation time and used directly with no runtime exchange, signing, or refresh, the same shape Magento's Integration token already uses.

**Error handling is fundamentally different from every REST connector in this repository.** Saleor's GraphQL view returns HTTP 200 for almost every outcome, including authentication and permission failures -- it only returns HTTP 400 when the server refuses to execute the query at all (parse/validation/query-cost rejection). Verified directly against Saleor's own published core source (`saleor/graphql/views.py`'s `get_response`, which only sets `status_code = 400` when `execution_result.invalid`). Consequently this connector inspects the top-level GraphQL `errors[].extensions.exception.code` field -- set by Saleor's own error formatter to the Python exception class name (`saleor/graphql/utils/__init__.py`'s `format_error`) -- rather than relying on HTTP status codes to distinguish success from an auth/permission rejection.

Saleor's storefront-facing model separates SKU (on `ProductVariant`) from the shared display name and publication state (on `Product`), unlike the single flat product row every other storefront connector in this repository addresses. Every `ProductVariant.sku` is projected as its own single-variant `sdk.RemoteProduct` row (the same flattened simplification WooCommerce/Shopware/Magento already make for their own parent/child variant models), with `Title` reading and writing the shared parent `Product.name` -- a deliberate, documented trade-off (see capability-audit.md) since Saleor has no per-variant display name field distinct from the shared product.

Channel and Warehouse are admin-supplied Saleor slugs, resolved to the entity ids the GraphQL API actually requires (`Query.channel(slug:)`, `Query.warehouses(filter:{slugs:})`) and cached in-memory per call -- the same pattern Shopware already uses to resolve its currency UUID from an ISO code. Money fields are parsed via `encoding/json.Number` to avoid float rounding, since Saleor's `Money.amount` is a GraphQL `Float`.

Pagination uses Saleor's native Relay-style cursor connections (`first`/`after`/`pageInfo.hasNextPage`/`pageInfo.endCursor`) for `productVariants` and `orders`, wrapped in a fingerprint-bound envelope like every other connector's cursor. `Order.grantedRefunds` (used for `returns.read`) is a plain list with no pagination arguments of its own, so it is windowed locally with an integer-offset cursor instead.

Official documentation: https://docs.saleor.io/api-reference/ ; schema and mutation shapes verified against the published GraphQL schema and Django view/webhook source at github.com/saleor/saleor.
