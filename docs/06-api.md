# API Architecture

REST base `/api/v1`; contract-first OpenAPI. OIDC bearer auth; tenant/workspace context derived from auth. Cursor pagination. Idempotency for retryable mutations. RFC7807-style problems. Correlation/request IDs.

## OpenAPI and production routing

The current v1 contract is the source of truth for the public HTTP operation
inventory. Every operation is registered by the production composition root. The route registry
is assembled in one place, and `openapi_runtime_parity_test.go` fails when an
OpenAPI operation has no production route or a non-HEAD production route is
absent from OpenAPI.

Lineage timeline, canonical legal-party search and master creation,
counterparty-role assignment, entitlement evaluation and the webhook
subscription/delivery API use their existing PostgreSQL-backed
services in production. Their organization/workspace scope is adapted only
from the authenticated request context installed by the mandatory OIDC,
tenant-resolution and authorization chain.

Task 111 replaces the nine former compatibility placeholders with production
adapters:

- connectors and counterparties read bounded tenant-scoped PostgreSQL
  projections;
- reconciliation jobs require an idempotency key and recheck the enabled sync
  policy plus the cabinet's current capability grant;
- settlements expose the append-only original-currency ledger with cursor
  pagination, while FX exposes immutable sourced reference facts;
- privacy requests create durable Task-061 workflows with opaque subject
  references and legally-significant audit evidence; execution stays
  fail-closed behind the deployment's configured store targets;
- Cloud subscription reads return explicit `community` mode when no Cloud
  subscription exists, so Community availability never depends on billing;
- upload admission requires a stable idempotency key and filename, stores only
  bounded bytes under an operator-configured S3-compatible tenant-derived
  quarantine key, and returns `QUARANTINED` metadata only;
- plugin listing combines reviewed public and tenant-private marketplace
  versions and excludes globally revoked artifacts/keys.

There is no hard-coded `501` route left in the production registry. Dependency
outages use bounded `503` responses and never promote pending/quarantined data.

Outbound webhooks are tenant-scoped, signed, retryable and replayable with delivery logs.

Report reads support JSON plus direct CSV/PDF downloads. Export representations
retain the authenticated report filters and tenant scope; PDF is generated by
the API and returned as `application/pdf`, not produced through browser print.

Connector accounts expose a separate capability control plane at
`PUT /connector-accounts:capabilities`. The request selects only capabilities
declared by that account's canonical manifest; omission means deny. Responses
include host-owned `read`/`write`, risk and approval metadata. Complete
snapshots are versioned with the account and audited, and sync execution checks
the current snapshot instead of treating the manifest as an account grant.

Task 106 adds `POST /connector-accounts:oauth-start` and
`POST /connector-accounts:oauth-callback`. Both require authenticated tenant
scope and idempotency. Start returns only a provider authorization URL and
expiry; callback returns only the disabled account projection. PKCE verifier,
client secret, authorization code and resulting tokens never enter API
responses. `POST /connector-accounts:check` now performs the manifest-declared
credential-aware remote HTTPS probe through bounded DNS-pinned egress and
persists only normalized health evidence.

Task 108 adds the cabinet bootstrap control plane. A metadata-only dry-run is
bound to the current account version and expires after 30 minutes. Initial
import consumes that evidence into a durable tenant-scoped dispatch job;
periodic incremental/full schedules are stored in PostgreSQL with optimistic
versions and never depend on an open browser. `GET
/connector-accounts:bootstrap` returns preview, schedule and fan-out progress;
entity/page progress and drift evidence remain canonical in Task-013
checkpoints and Task-014 reconciliation runs.

MCP exposes high-level tools with normal authz/approval/audit; no DB or raw secret tools. See `contracts/mcp-tools.md`.

The canonical party workflow is intentionally two-step: `POST /legal-parties`
creates a draft legal entity, individual entrepreneur or branch, and
`POST /counterparties` assigns a buyer, supplier, partner or other role to
that existing master. Both mutations require `Idempotency-Key`, are
tenant-scoped, and write audit/outbox/lineage evidence through the legal-party
repository. A missing master is rejected before a role can be created.


## Task 019 n8n surface

The official `n8n-nodes-torgnexa` package is an external client of this API. It receives only a scoped bearer credential and an absolute `/api/v1` base URL; organization/workspace selectors are not accepted. Product/Order actions use the same public search operations as other clients. The trigger provisions subscriptions through the public webhook API and deactivates them through the evidence-preserving `DELETE /webhook-subscriptions/{id}` lifecycle operation.
