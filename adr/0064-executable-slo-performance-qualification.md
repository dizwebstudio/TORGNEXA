# ADR 0064: Executable SLO and performance qualification

## Status
Accepted

## Context
Task 066 must turn the existing observability checklist into versioned, executable service-level objectives for API, Kafka/event processing, synchronization/reconciliation, durable webhooks and reporting. A shared CI runner cannot honestly establish production capacity, while leaving performance as prose allows thresholds and workload profiles to drift without review.

## Decision
Introduce `internal/platform/slo` as the host-owned evaluator for availability, nearest-rank p50/p95/p99 latency, throughput, lag, saturation and 30-day error-budget math. Commit deterministic load/failure profiles and a normalized baseline generated by `cmd/torgnexa-slo-report`; `make performance` regenerates and diffs that report so threshold or profile drift fails closed.

The repository baseline is explicitly hardware-neutral and qualifies the SLO machinery, not production QPS. Production release repeats the same objectives with real telemetry from the exact deployment topology and retains commit/image, hardware, replicas/partitions, dataset, concurrency, duration and software-version evidence. External marketplace/provider availability is excluded from TORGNEXA host availability and is measured separately as dependency health/freshness.

## Alternatives considered
Wall-clock microbenchmarks on arbitrary CI runners were rejected as release thresholds because noisy shared hardware creates flaky gates and misleading capacity claims. Prose-only SLO documentation was rejected because it cannot prevent silent budget relaxation. Folding remote marketplace uptime into TORGNEXA availability was rejected because the product does not control those services.

## Compatibility impact
Additive operational capability only. No public HTTP/OpenAPI operation, event schema, Connector SDK or provider contract changes.

## Migration and data impact
No PostgreSQL or ClickHouse migration is required. The committed baseline is repository evidence, not customer or tenant data.

## Security and privacy impact
Observations are bounded numeric latency/count/lag/capacity values. The SLO contract never requires request bodies, event payloads, headers, credentials, tenant identifiers or remote diagnostic dumps.

## Operational impact
`make performance` becomes part of the repository check path. Staging/production qualification must supply real observations for the same objectives. Task 077 consumes sustained objective breaches and error-budget burn to define paging and executable incident response.

## Consequences
Performance budget changes require reviewed repository changes instead of ad-hoc operational tuning. CI remains deterministic, while production capacity evidence remains topology-specific and cannot be inferred from the normalized repository baseline.
